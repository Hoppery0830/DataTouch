# 织物触觉舒适度检测平台 — 产品端方案对比

> 目的：决定"用户侧"（WiFi 配网 + 实时显示）在产品化后用哪种形态落地。
> 当前进度：ESP32-S3 网关（WiFi + WebSocket + 手机网页实时显示）已跑通（DEMO）。

> **命名约定**：本套文档统一用 **产品形态 A/B/C** 指"用户侧形态"——**产品形态 A = 设备自带网页**、**产品形态 B = 微信小程序 + 云**、**产品形态 C = 原生手机 App**。
> **配网方式**另用**非冲突编号**——**配网方式 ① = 保留热点(APSTA)**、**配网方式 ② = 连上后关热点用 IP（当前采用）**。
> 请勿再用"方案 A/B"指代配网方式（旧文档里两者混用，已按上述命名区分）。

---

## 1. 核心约束（必须知道）

- 微信小程序**真机**（预览/体验版/正式版）的 `wx.request` / `wx.connectSocket`
  只允许 **HTTPS / WSS**，且目标域名必须加进微信后台"**服务器域名**"白名单；
  该域名一般还需 **ICP 备案**。
- **局域网 IP（`192.168.x.x`、`10.x.x.x`）无法加入白名单** → 真机小程序**连不上设备的局域网 IP**。
- 只有**微信开发者工具**里勾选"不校验合法域名、TLS 版本以及 HTTPS 证书"才能连 `ws://<ip>:81`。

这决定了：**小程序要做真机，就必须走"云端中转"**；而"设备自带网页"天然是本地/离线方案。

---

## 2. 三种候选产品形态概况

| | 产品形态 A：设备自带网页 | 产品形态 B：微信小程序 + 云端中转 | 产品形态 C：原生手机 App |
|---|---|---|---|
| 一句话 | 设备自己当服务器 + 门户配网 | 设备推数据到云，小程序从云读 | 专门 App，本地/云端皆可 |
| 配网 | 门户网页（Captive Portal） | BLE 配网（较复杂） | BLE 配网（直接） |
| 实时显示 | 设备 WebSocket 直连 | 云端中转 | 设备直连（BLE/局域网） |
| 服务器/域名/备案 | **不需要** | **必须** | 视需求（本地则免） |
| 离线可用 | **强** | 弱（依赖云） | 强（本地） |
| 微信生态/云历史/多设备/通知 | 弱 | 强 | 强 |
| 安装/账号 | 零安装零账号 | 用微信 | 下载 App + 可能账号 |
| 开发工作量 | **小** | **大** | 中大 |
| 量产/运维成本 | 最低 | 需服务器运维 | 需 App 维护 |
| 真机可用（今天） | ✅ 已验证 | ❌ 需先上服务器 | 需开发 |

## 3. 产品形态 A：设备自带网页（推荐：最快成产品）

### 3.1 配网流程（Captive Portal，业界标准）
1. 设备首次上电 → 开热点（如 `YD-ESP32S3`）。
2. 用户手机连上该热点。
3. 手机浏览器打开 `192.168.4.1`（做了 DNS 劫持后，多数手机会**自动弹出**配置页）。
4. 配置页显示表单："请输入家里 WiFi 的 SSID 与密码"。
5. 设备保存 → 自动重启进入 STA 模式，加入家里 WiFi。
6. 用户重新连回家里 WiFi，访问设备新 IP 即可使用。

> 步骤 2~4 一次性完成，之后无需再配。

### 3.2 显示与功能
- 实时曲线（力/位移）、分项指标、综合评分、状态机控制（ARM/START/STOP/RESET）。
- 历史曲线/历史记录（存设备 SD 卡 / 本地）。

### 3.3 产品化还需补的功能
- **mDNS**：让用户访问 `http://datatouch.local/`，免记 IP。
- **Captive portal 自动弹出**：设备内置 DNS 服务器，把所有 DNS 请求指向自己，浏览器自动跳转到配置页。
- **NVS 持久化**：WiFi 凭据存进非易失存储，掉电不丢。
- **恢复配网兜底**：长按按钮 5 秒 → 擦除凭据，回到 AP 配网模式。
- **本地历史**：曲线/评分写 SD 卡，页面提供历史回看。

### 3.4 优点
- 零安装、零账号、离线可用，任何手机/浏览器都能用。
- 不需要服务器、域名、备案、HTTPS —— 成本最低、上线最快。
- 符合任务书交付物"网页端实时显示界面"。

### 3.5 局限
- 无云端历史、无跨设备/多用户、无推送通知。
- 发现方式需靠 mDNS / 二维码 / 门户跳转，用户要开浏览器。
- 持续演进成"消费者云产品"时，需要再叠加产品形态 B。

## 4. 产品形态 B：微信小程序 + 云端中转（真机友好，但重）

### 4.1 数据流
```
ESP32 --WSS(客户端)--> 云服务器/MQTT Broker <--WSS/HTTPS--> 微信小程序
       发布 topic                     订阅 topic
```
- ESP32 作为**客户端**主动连云端（发布），小程序作为客户端连云端（订阅/接收）。

### 4.2 两种中继实现
| 实现 | 硬件/资源 | 成本 | 说明 |
|---|---|---|---|
| 自建 WS 中继服务器 | 服务器 + 备案域名 + TLS | ~¥100–300/年 | 最可控，数据私有 |
| 公网 MQTT Broker | 无 | 免费 | 现成 broker（如 `broker.emqx.io`）；数据公开，且**未必能过微信白名单**（备案要求），有风险 |

### 4.3 配网：必须 BLE
因为小程序真机连不上设备局域网 IP，配网走**蓝牙**：
`wx.openBluetoothAdapter → 扫描设备 → 配对 → 把 WiFi 凭据写给设备 → 设备重启进 STA → 上报云端`。
（开发复杂度明显高于网页门户配网。）

### 4.4 需要准备的资源
1. 云服务器；2. ICP 备案域名；3. TLS 证书（WSS）；4. 微信公众平台加白名单；5. 微信小程序账号 + AppID。

### 4.5 优点
微信生态体验好、可分享、可做云端历史/多设备/通知。

### 4.6 缺点 / 坑
- 必须服务器 + 备案（2–4 周，是主要瓶颈）。
- 设备须**保持在线**推数据，否则小程序看不到（本地/离线场景差）。
- BLE 配网复杂；公共 broker 白名单不可控。

---

## 5. 产品形态 C：原生手机 App（备选）
- 配网用 BLE，显示可本地（BLE/局域网）或上云。
- 体验最好、最可控，但**开发与维护成本最高**，且用户要下载安装、可能注册账号。
- 通常只用于"专业级/消费级"产品，学生/低成本项目一般不必选。

---

## 6. 成本与时间（粗略估算）

| 项 | 产品形态 A | 产品形态 B | 产品形态 C |
|---|---|---|---|
| 开发工作量 | 小（~数天） | 大（小程序+服务器+BLE，数周） | 中大（数周~月） |
| 服务器/域名/备案 | 无 | 有（服务器年费 + 备案时长） | 视情况 |
| 上线/评审 | 无需 | 需微信审核 | 需应用商店上架 |
| 真机演示 | 已可用 | 需先部署云 | 需开发完 |

> 若走产品形态 B，备案是时间瓶颈，务必**提前**启动。

---

## 7. 推荐路线（分阶段，风险最小）

- **阶段一（现在，推荐）**：把**产品形态 A（设备网页）**落地——
  补 mDNS、Captive portal 自动弹出、NVS 存 WiFi、恢复配网、本地历史。
  这**已满足任务书"网页端实时显示界面"交付物**，零服务器、离线可用、最快可交付。
- **阶段二（可选，二期）**：确认要走消费者云产品时，再叠加 **产品形态 B**——
  设备加 BLE 配网 + 云端中继，数据流/评分逻辑**原样复用**，只改传输层。

---

## 8. 结论与决策建议

- **只要你目标是"低成本、实验室/单机、本地查看"** → **选产品形态 A（设备网页）**，最快且最稳。
- **如果你确要认真做"消费者云产品、要微信生态/云端历史/多设备"** → 选**产品形态 B**，但要**先评估服务器 + 备案**，且配网改成 BLE。
- **可先 A 后 B**：先把产品形态 A 做成可交付，产品形态 B 作为二期演进，避免一开始就被备案/服务器拖死。

> 一句话：**"用户输 WiFi"这个问题，网页端用门户配网就能很好解决；小程序非但没让它更简单，反而要引入 BLE 配网 + 云端。** 所以不一定"最后用小程序更好"，关键看你目标用户。
